Rule of thumb: **say what was tested against what.** "Real" means exercised against a real system, "simulated" means
fixtures or mocks, "synthetic" means the data itself was generated.

## 2. Suggested resume wording

Pick the line that matches what you can defend in an interview. Each one is true as written.

**Discovery and validation**
> Built a provider-adapter architecture that discovers and validates TLS certificates (expiry, hostname match, key strength, trust chain, OCSP revocation) from live endpoints and Kubernetes Secrets, with AWS ACM (tested against moto) and Azure/GCP adapters (fixture-backed); FastAPI, SQLAlchemy/PostgreSQL, scheduled jobs with retries and persisted run state.

**Risk model**
> Trained a scikit-learn gradient-boosting certificate-risk model on a documented synthetic simulator and evaluated it against a rule-based baseline with team-grouped splits and bootstrap confidence intervals (ROC-AUC 0.86 vs 0.69; synthetic data only, so no real-world accuracy claim).

**Agent**
> Built a LangChain agent (Gemini) with nine guarded tools for inventory queries, root-cause analysis and renewal planning: tool allow-list, role-based tool sets, call budgets, timeouts, an audit trail, and a human-approval gate the agent cannot bypass (verified with misbehaving-model tests and a 28-case evaluation harness; live-model accuracy not yet measured).

**Renewal**
> Implemented a human-approved ACME renewal workflow (dry-run plan, signed-in approval, single-use execution) tested end to end against a local Pebble CA with issued keys stored in HashiCorp Vault; concurrency-tested on PostgreSQL.

**Engineering quality**
> Shipped with automated backend, frontend and integration test suites (real Pebble, Vault, PostgreSQL and Kubernetes; exact counts in section 3), ruff and dependency-audit gates, Alembic migrations, and a GitHub Actions pipeline.

## 4. Wording to avoid

| Don't say | Why |
|---|---|
| "X% accuracy" / "predicts outages" for the risk model | the data is synthetic |
| "Agent achieves 100%" | the 100% is a scripted stand-in model measuring workflow behavior, not Gemini |
| "Multi-cloud discovery across AWS, Azure and GCP" (unqualified) | AWS is mock-tested; Azure and GCP are fixtures |
| "Fully automated renewal" / "zero-touch renewal" | a human approves every execution and deployment is manual |
| "Let's Encrypt integration" (unqualified) | exercised against Pebble only |
| "Vault PKI" | only Vault KV (secret storage) is implemented |
| "Production-ready" | single-process scheduler, no deployment automation, notifications never run live |

## 5. Questions you should be ready for

* *"How do you know the validator is right?"* Lab with 11 scenarios plus a local OCSP responder, asserted in tests; the original code reported self-signed certificates as valid and OCSP had never worked, and both are now covered by tests.
* *"Your model beats the baseline; so what?"* At the operating threshold it ties on F1; the gain is ranking, and much of it comes from features the simulator was wired to reward.
* *"What stops the agent renewing something it shouldn't?"* It cannot approve; execution needs a human-approved, unexpired, unchanged, single-use plan, enforced in `RenewalService` and tested with a deliberately misbehaving model.
* *"Why is the eval 100%?"* It measures the tool layer and guardrails with a stand-in model, and it fails when guardrails are deliberately broken; it says nothing about Gemini.
